CLAUDE.md

ตำแหน่ง: วางไว้ที่ Root โฟลเดอร์ของโปรเจ็ค (./CLAUDE.md)

สำคัญที่สุด (Must Have)

📌 ในไฟล์ CLAUDE.md ต้องใส่อะไรเข้าไปบ้าง?

CLAUDE.md เปรียบเสมือน Onboarding Document และ สมองประจำโปรเจ็ค ที่ Claude Code จะเปิดอ่านทุกครั้งก่อนเริ่มทำงาน เพื่อให้ AI เข้าใจบริบทได้ทันทีโดยไม่ต้องถามซ้ำ ควรมี 6 หมวดสำคัญดังต่อไปนี้:

1. Project Overview & Architecture

อธิบายว่าโปรเจ็คนี้ทำอะไร มีเป้าหมายอะไร สถาปัตยกรรมแบบไหน (เช่น Clean Architecture, MVC, Microservices) และผังโฟลเดอร์หลัก เช่น src/core/, src/api/

2. Tech Stack & Environment

ระบุ Runtime, ภาษา, Framework และ Database พร้อมเวอร์ชัน เช่น Node.js 20+, TypeScript 5.x, Next.js 15, PostgreSQL, pnpm เพื่อป้องกัน AI เขียนโค้ดด้วย API เวอร์ชันเก่า

3. Essential Operational Commands

คำสั่งใช้งานจริงที่ AI รันได้ทันที: คำสั่ง Install, Dev server, Production build, คำสั่งรัน Test (ทั้งหมด, เจาะจงไฟล์เดียว, watch), Lint, และ Typecheck

4. Coding Standards & Patterns

กฎการตั้งชื่อไฟล์/ตัวแปร/ฟังก์ชัน, ห้ามใช้ any, รูปแบบการดักจับ Error และข้อกำหนดว่าต้องเขียน Unit test คู่กับโค้ดใหม่เสมอหรือไม่

5. Git & Workflow Guidelines

การตั้งชื่อ Branch (feat/, fix/) และรูปแบบ Commit Message ตาม Conventional Commits (feat:, fix:, refactor:)

6. Security & Safety Rules

กฎเหล็กความปลอดภัย เช่น ห้าม Commit Secret/API Keys เด็ดขาด, ห้ามรันคำสั่งลบฐานข้อมูลโดยไม่ถาม และการ Validate Input ก่อนส่งเข้า Database

ตัวอย่างโค้ดจริงในไฟล์ CLAUDE.md สำหรับนำไปใช้: 
# Project Guidelines for Claude Code

## 1. Project Overview & Architecture
- **Project Name**: My-Awesome-App
- **Description**: Next.js 15 e-commerce application with Stripe payment integration.
- **Key Modules**:
  - `src/app/`: Next.js App Router pages and API route handlers
  - `src/components/`: Reusable UI components (Tailwind CSS + Radix UI)
  - `src/lib/`: Shared utilities, database client, and Stripe helpers
  - `src/services/`: Business logic layer (Orders, Products, Checkout)
  - `tests/`: Vitest unit and integration test suites

## 2. Tech Stack & Environment
- **Runtime**: Node.js 20 LTS
- **Language**: TypeScript 5.5+ (Strict mode enabled)
- **Framework**: Next.js 15 (App Router, React Server Components)
- **Database**: PostgreSQL (Prisma ORM)
- **Package Manager**: pnpm

## 3. Essential Commands
### Development & Build
- Install dependencies: `pnpm install`
- Start dev server: `pnpm run dev`
- Production build: `pnpm run build`
- Database migrations: `pnpm prisma migrate dev`

### Testing & Verification
- Run all tests: `pnpm test`
- Run single test: `pnpm test -- src/services/order.test.ts`
- Run test coverage: `pnpm test -- --coverage`
- Lint check: `pnpm run lint`
- Type checking: `pnpm run type-check`

## 4. Coding Standards & Conventions
- **Naming**: `kebab-case` for files/folders, `PascalCase` for React components/types, `camelCase` for functions.
- **Type Safety**: Strictly avoid `any`; use explicit interfaces or `unknown` with type guards.
- **Error Handling**: Use custom Result types or try/catch with typed domain errors. Never swallow exceptions silently.
- **Testing**: Every new service function must include a corresponding unit test in `*.test.ts`.

## 5. Git & Workflow Guidelines
- **Branches**: `feat/`, `fix/`
- **Commits**: Follow Conventional Commits (e.g., `feat(order): add stripe webhook handler`)
- **PR Requirement**: All tests and type checks must pass before merging.

## 6. Safety & Security Rules
- **NEVER** hardcode or commit API secrets (Stripe Secret Key, DB URLs). Always read from `process.env`.
- Do not run `prisma migrate reset` in production or without explicit confirmation.
- Validate all incoming request payloads using Zod schemas.
💡 Tips สำหรับ CLAUDE.md:

• ระบุคำสั่งเฉพาะไฟล์เดี่ยว เช่น pnpm test -- <file> เพราะ AI จะได้ไม่ต้องรันเทสต์ทั้งโปรเจ็คทุกครั้ง ประหยัดเวลาได้มหาศาล

• หากโปรเจ็คของคุณมีการเปลี่ยนแปลงสถาปัตยกรรม ให้อัปเดตไฟล์นี้เสมอ เพื่อให้ Claude รู้อยู่ตลอด

# /review Command
Review recent workspace code changes against project standards.

## Instructions
1. Run `git status` and `git diff` to inspect modified code.
2. Evaluate: Correctness, Edge Cases, Security (no secrets), and Test Coverage.
3. Output format:
   - Summary of Changes
   - Critical Issues (Blockers)
   - Improvements / Suggestions
   - Verdict: Approve / Request Changes
คำสั่งที่ 2: .claude/commands/commit.md (เรียกใช้งานด้วย /commit) 
# /commit Command
Prepare a clean Conventional Commit message for staged changes.

## Instructions
1. Run `git status` and `git diff --cached`.
2. Format message: `(): ` (types: feat, fix, docs, refactor, test, chore).
3. Keep subject line under 72 chars, imperative mood.
4. Present the command `git commit -m "..."` for user confirmation.

Always-on Rules

📌 ในไฟล์ GEMINI.md ต้องใส่อะไรเข้าไปบ้าง?

GEMINI.md (หรือ AGENTS.md) คือ กฎระดับ Workspace ที่ระบบของ Antigravity จะสแกนหาแบบ Hierarchical จาก CWD ขึ้นไปจนถึง Git Root และถูกโหลดเข้าสู่บริบทการทำงานตลอดเวลา (Always-on) ควรประกอบด้วย 5 หมวดหลัก:

1. Project Mission & Architecture Boundaries

ระบุขอบเขตของโปรเจ็ค โครงสร้างโฟลเดอร์ และหน้าที่ของแต่ละเลเยอร์ (เช่น Domain, Application, Infrastructure) เพื่อให้ Agent รู้ว่าต้องเพิ่มโค้ดที่ไฟล์ไหน

2. Standard Operational Commands

คำสั่ง Build, Development Server, Unit/Integration Test, Linting, และ Type Checking ที่แน่นอน

3. Behavioral Rules for Agent

กำหนดพฤติกรรมของ Antigravity: ต้องอธิบายเหตุผลก่อนลงมือแก้, ทำการแก้ไขเฉพาะจุดที่จำเป็น (Minimal diffs), และต้องรันคำสั่ง Verify หลังแก้เสร็จเสมอ

4. Security & Destructive Action Guardrails

กฎห้ามเปิดเผยหรือ Commit ความลับ (API keys, Tokens), ห้ามรันคำสั่งทำลายล้าง เช่น rm -rf, git reset --hard หรือคำสั่ง Drop Database

ตัวอย่างโค้ดจริงในไฟล์ GEMINI.md สำหรับนำไปใช้: 
# Project Rules & Guidelines for Google Antigravity

## 1. Project Overview & Architecture
- **Project Name**: Cloud-Payment-Gateway
- **Core Mission**: High-throughput transaction processing API with strict idempotent handling.
- **Architecture Layers**:
  - `src/domain/`: Core business models, entities, and validation invariants.
  - `src/application/`: Use cases, transaction orchestrators, command handlers.
  - `src/infrastructure/`: Database adapters (PostgreSQL), external bank clients, message queues.
  - `src/interfaces/`: HTTP API controllers and OpenAPI schemas.
  - `tests/`: Automated unit and integration test suites.

## 2. Tech Stack & Environment
- **Runtime**: Python 3.12 (Managed via `uv`)
- **Framework**: FastAPI + Pydantic v2
- **Database**: PostgreSQL 16 (SQLAlchemy 2.0 Async + Alembic)
- **Cache**: Redis 7.2

## 3. Standard Operational Commands
- Environment Sync: `uv sync`
- Start Dev Server: `uv run uvicorn src.interfaces.http:app --reload --port 8000`
- Run All Tests: `uv run pytest`
- Run Single Test File: `uv run pytest tests/test_payment.py -v`
- Lint & Format Check: `uv run ruff check .`
- Auto-format Code: `uv run ruff format .`
- Static Type Checking: `uv run mypy src`

## 4. Agent Behavioral Rules
1. **Explain Rationale**: Before invoking file replacement or write tools, explain the architectural reason in 1-2 concise sentences.
2. **Minimal & Targeted Diffs**: Only modify lines relevant to the prompt. Do not reformat unaffected code or delete existing comments.
3. **Verify Every Change**: Always run `pytest` or `ruff check` on modified files after completing an edit.
4. **Preserve Compatibility**: Never alter existing public API schemas without explicit instructions.

## 5. Security & Safety Constraints
- **Zero Secrets Policy**: Never print, log, or commit secret keys or bearer tokens. Always inject via `.env`.
- **Destructive Commands Blocked**: Never run `rm -rf`, `DROP DATABASE`, or `git checkout -- .` without asking first.
- **Strict Input Validation**: Every request body must be parsed through a Pydantic schema with bounds checking.
💡 ข้อกำหนดสำคัญของ GEMINI.md (Antigravity Constraints):

• ไม่ต้องใส่ YAML Frontmatter ในไฟล์ GEMINI.md หรือ AGENTS.md ที่วางไว้ที่โฟลเดอร์

• จำกัดขนาดสูงสุด 24 KB / 24,000 bytes ต่อไฟล์ และแชร์โควตากฎรวมที่ 20,000 tokens หากยาวเกินไป ระบบจะลดระดับไปเป็น pointer อ่านตามต้องการแทน

• หากมีกฎเฉพาะทาง เช่น กฎ Frontend หรือ Database แนะนำให้แยกไปไว้ใน .agents/rules/

Progressive Disclosure

📌 ระบบ Progressive Disclosure ของ Skills ทำงานอย่างไร?

Skills คือรันบุ๊กขั้นตอนทำงาน (Procedures) ที่ฉลาดมากใน Antigravity เพราะ จะไม่ถูกโหลดเนื้อหาเต็มเข้า Context Window ทันที โดยตอนเริ่ม Agent จะอ่านเฉพาะ name และ description จาก YAML Frontmatter เท่านั้น และจะเปิดอ่านเนื้อหาเต็มเมื่อผู้ใช้สั่งงานที่ตรงกับ Description นั้นๆ

โครงสร้างโฟลเดอร์ของ 1 Skill ที่ถูกต้อง:

# Code Review Skill

This skill guides the agent through an objective review of workspace modifications.

## Procedure

1. **Inspect Working Tree & Staged Changes**:
   - Check status and diff using git commands:
     ```bash
     git status
     git diff
     ```
2. **Review Against Architectural & Quality Standards**:
   - Consult the detailed [Review Checklist](./references/checklist.md) for quality, performance, and security rules.
   - Verify that all new logic includes appropriate unit/integration tests.
3. **Run Automated Quality Checks**:
   - Execute project linter and test suite to ensure no regressions.
4. **Formulate Review Feedback**:
   - **Summary**: Concise bullet points describing the intent and scope of changes.
   - **Critical Findings**: Bugs, security vulnerabilities, or breaking changes.
   - **Recommendations**: Optional improvements for style, performance, or clarity.
   - **Approval Status**: `Approve`, `Comment`, or `Request Changes`.

# Workspace Coding Standards & Quality Gates

## 1. Type Safety & Contracts
- All new code must be fully type-annotated.
- Avoid escape hatches like `any` or untyped dictionaries for core domain models.
- Validate external input contracts using schema validation (e.g. Zod, Pydantic).

## 2. Error Handling
- Never suppress exceptions with empty `catch` or `except: pass` blocks.
- Throw or return typed errors with clear contextual messages and error codes.
- Ensure all resources (file handles, database connections) are closed properly.

## 3. Testing Standards
- All bug fixes must be accompanied by a regression test reproducing the issue before the fix.
- New domain or utility logic must achieve unit test coverage.
- Avoid testing implementation details; test behaviors, inputs, and outputs.

Automated Guardrails

📌 หน้าที่และตัวอย่างการใช้งาน Lifecycle Hooks:

ไฟล์นี้ช่วยให้คุณสั่งรันคำสั่งเชลล์ภายนอก ณ จุดเวลาต่างๆ ในลูปการทำงานของ Agent ได้โดยอัตโนมัติ:
• PreToolUse: ตรวจสอบความปลอดภัยก่อน Agent จะรันคำสั่ง
• PostToolUse: รัน Linter ตรวจสอบโค้ดทันทีหลังจาก Agent แก้ไขไฟล์ (replace_file_content)

ตัวอย่างโค้ดใน .agents/hooks.json: 
{
  "lint-on-change": {
    "enabled": false,
    "PostToolUse": [
      {
        "matcher": "replace_file_content",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint --silent || true",
            "timeout": 15
          }
        ]
      }
    ]
  },
  "pre-command-safety": {
    "enabled": false,
    "PreToolUse": [
      {
        "matcher": "run_command",
        "hooks": [
          {
            "type": "command",
            "command": "echo '[HOOK] PreToolUse validation passed'",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
